# Контракт із пайплайном

Найнезвичніша частина проєкту: половина системи виконується **не на сервері**,
а на ноутбуці власника, раз на місяць, і спілкується з беком через сім
ендпоінтів. Аналогів у звичайній веброзробці в цього немає, тому розписано
детально.

Схема таблиць — `BACKEND.md` §4–§8, цикл цілком — §9. Тут те, що потрібно, коли
пишеш саме ці ендпоінти.

## Чому пайплайн узагалі локальний

Джерело закладів — вивантаження OpenStreetMap на всю Україну, файл близько
гігабайта. Його ріжуть `osmium` і DuckDB, повний прогін чотирьох міст іде
близько сорока секунд, і з них тридцять три — вирізання bbox.

Возити цей гігабайт на сервер немає ніякого сенсу: результат — сім із половиною
тисяч записів, менше двох мегабайтів. Тому важке лишається локально, а на
сервер їде тільки результат.

## Порядок і чому саме такий

```
1. PULL     GET  /api/pipeline/overlay          база → curated/*.json
2. ПРОГІН   npm run fetch:places                локально, логіка без змін
3. PUSH     POST /api/pipeline/*                результат → база
4. БАНДЛИ   бек збирає з бази                   база → статичні JSON
```

**PULL мусить бути першим і мусить бути свіжим.** Пайплайн перезбирає заклади
з джерел із нуля — усе, що людина зробила руками за місяць, приїжджає з бази
саме на цьому кроці. Прогін зі вчорашньою накладкою мовчки поверне на карту
все, що прибрали.

Тому `fetch-places.js` перевіряє `generatedAt` і **падає**, якщо накладці
більше доби.

## GET /api/pipeline/overlay

Уся накладка одним файлом. Викликається раз на прогін, тому ділити на сторінки
не треба — обсяг маленький.

```json
{
  "generatedAt": "2026-09-01T10:00:00Z",
  "counts": { "removals": 143, "edits": 27, "additions": 5, "aliases": 2, "suspects": 61 },

  "removals": {
    "kv_f27208dd": { "source": "manual", "why": "перевірив на місці", "at": "2026-08-30" }
  },
  "edits": {
    "dnpr_a0d7326b": { "lat": 48.4620001, "lng": 35.0530002, "address": "Барикадна вулиця 6" }
  },
  "additions": [
    { "uid": "kv_9a1b2c3d", "city": "kyiv", "name": "…", "kind": "cafe", "lat": 50.44, "lng": 30.52 }
  ],
  "aliases":  { "kv_old11111": { "keep": "kv_new22222", "source": "manual" } },
  "suspects": { "kv_707400bd": "closed" },
  "merges":   { "kv_1df77535 kv_e5c1f2cd": { "verdict": "same", "keep": "kv_e5c1f2cd" } },
  "notOurs":  [ "Beer Market", "Hop Hey" ],
  "googleLinks": {
    "osm:n10003860121": {
      "gid": "ChIJ…", "status": "OPERATIONAL", "score": 1,
      "checkedAt": "2026-08-28", "statusAt": "2026-08-29"
    }
  }
}
```

Куди який ключ лягає локально:

| Ключ | Файл | Що з ним робить прогін |
|---|---|---|
| `removals` | `curated/dropped.json` | `source: manual` — викидає заклад із бандла й не питає Google |
| `edits` | `curated/edits.json` | накладає поверх джерел останнім кроком |
| `suspects` | `curated/closed-suspects.json` | вердикт `closed` викидає, `keep` більше не питає |
| `googleLinks` | `curated/place-ids.json` | `gid` і статус; `CLOSED_PERMANENTLY` викидає з бандла |
| `merges` | `curated/dupe-suspects.json` | `same` зводить пару, `different` більше не питає |
| `notOurs` | `curated/not-ours.json` | назви мереж, яких на карті не буває |
| `aliases` | `curated/twins.json` | зайвий запис пари не потрапляє в бандл, дані переїжджають до того, що лишився |
| `additions` | — | у прогоні не бере участі, потрібне лише для пошуку дублів |

**`removals` віддаються всі, з будь-яким `source`.** Пайплайн сам розбереться:
`manual` він читає й ніколи не чіпає, `google` і `osm` — його власні, він їх
перезаписує. Фільтрувати на боці беку не треба, інакше прогін втратить свої ж
надгробки й перепитуватиме закриті заклади щомісяця, витрачаючи квоту.

**`counts` — не декорація.** Локальний скрипт звіряє кількість рядків у кожній
секції з цим числом і відмовляється писати файли, якщо не збіглось. Обрив
з'єднання посеред великого JSON інакше дав би валідний, але обрізаний файл.

## POST-ендпоінти заливки

```
POST /api/pipeline/runs               → { runId: 42 }
POST /api/pipeline/places             чанками по 500
POST /api/pipeline/uids               чанками по 500
POST /api/pipeline/google-links       чанками по 500
POST /api/pipeline/merge-candidates
POST /api/pipeline/runs/42/finish     → { rowsUpserted: 7592 }
```

Правила, спільні для всіх:

1. **Тільки `UPSERT` по `uid`** (для `place_uids` і `google_links` — по
   `osm_id`). Ніякого `TRUNCATE`, ніякого масового `DELETE`.
2. **`WHERE origin = 'osm'`** у кожному записі в `places`.
3. **Транзакція на чанк.** Не одна на всю заливку: пʼятнадцять чанків по 500 у
   спільній транзакції тримають блокування хвилинами.
4. **Ідемпотентність.** Той самий чанк, надісланий двічі (мережа обірвалась,
   скрипт повторив), не має дати іншого результату.
5. **`run_id` обовʼязковий.** Запис без відкритого прогону — `409`.

`finish` робить три речі: закриває рядок у `pipeline_runs`, ставить
`bundles.dirty = 1` містам зі списку і повертає підсумок, який скрипт друкує
в консоль.

## Чого пайплайн від беку НЕ чекає

- **Не чекає, що бек перевірить дані.** Валідація формату — так; змістовна
  перевірка — ні, вона вже відбулась локально.
- **Не чекає синхронної збірки бандлів.** `finish` повертається одразу,
  перезбірка йде своїм cron'ом.
- **Не читає нічого, крім `overlay`.** Стан закладів у нього свій, локальний.

## Що ламається найчастіше

**Правки між PULL і PUSH.** Прогін іде хвилини, резолв Google — годинами. Якщо
людина в цей час щось виправила, локальний бандл її правки не міститиме. Це не
проблема: локальний бандл — чернетка, у продакшн їде той, що бек збирає з бази
вже після заливки. **Тому локальні бандли нікуди не публікуються.**

**Заклад зник із джерела.** Він міг випасти з bbox, маппер міг зняти тег, OSM
міг глюкнути. Ставиться `last_run_id` тим, хто приїхав; хто не приїхав кілька
прогонів поспіль — у список на перегляд, а не під `DELETE`.

**Квота Google.** Пʼять тисяч безкоштовних запитів на місяць — жорсткий бюджет,
на який претендують дві задачі: пошук нових закладів (по клітинках сітки) і
перевірка статусів у тих, де `gid` уже є (по одному запиту на заклад). Разом
вони в місяць не влазять, тому прогони чергуються: `--status` проводить саму
перевірку й спиняється до пошуку. Бек на це не впливає, але має бути готовий, що
`resolve` приходить не щомісяця й не по всіх містах, а `checked_at` і
`status_at` розʼїжджаються на місяці.

## Одноразова міграція

Перше, що взагалі треба зробити: залити в порожню базу те, що зараз лежить у
`pipeline/curated/` і в бандлах. Це `migrate:curated` — скрипт на боці пайплайна,
який ходить у ті самі POST-ендпоінти.

Порядок важливий: `place_uids` → `places` → `place_contacts` і `place_media` →
`google_links` → `place_uid_aliases` → `place_removals` → `place_edits`. Накладка
**останньою**, щоб не впертись у перевірки цілісності на півдорозі.

Псевдоніми йдуть перед надгробками не випадково: надгробок із `source = 'dupe'`
посилається на `uid`, у який злили, і без псевдоніма він ні про що.

Окремо про `google_links`: у файлі є записи, де два `osm_id` мають один `gid` —
до 29.08.2026 обмеження `UNIQUE KEY uq_gid` не існувало. Міграція на таких
падатиме, і це правильно: спершу розсудити спір локально, потім заливати.

**Критерій, що міграція вдалась:** бандл, зібраний із бази, збігається з тим,
що зараз лежить у `public/places/`, з точністю до порядку ключів. Поки не
збігається — переїзду не сталось, і рухатись далі немає сенсу.
