# Інваріанти й перевірки

Одинадцять правил із `BACKEND.md` §14, кожне з тим, як воно ламається на практиці
і як це зловити. Порушення жодного з них не падає з помилкою — усі вони
проявляються згодом і тихо.

Запити нижче написані так, щоб **порожня відповідь означала «все гаразд»**.
Їх варто винести в тест і ганяти в CI, а не запускати руками раз на пів року.

---

## 1. Пайплайн не пише в накладку і в контур людей

Виняток єдиний: рядки `place_removals` із `source` у `('google','osm')`.

**Як ламається.** Хтось додає в заливку зручності: «заодно перерахуємо
`user_places`», «заодно приберемо застарілі правки». Наступний прогін стирає
місяць чужої роботи.

**Перевірка — на рівні прав, а не сподівань.** Окремий користувач MySQL для
ендпоінтів пайплайна:

```sql
GRANT SELECT, INSERT, UPDATE ON smakoteka.places        TO 'pipeline'@'%';
GRANT SELECT, INSERT, UPDATE ON smakoteka.place_uids    TO 'pipeline'@'%';
GRANT SELECT, INSERT, UPDATE ON smakoteka.google_links  TO 'pipeline'@'%';
GRANT SELECT                  ON smakoteka.place_edits  TO 'pipeline'@'%';
-- на users, user_places, user_sessions, proposals прав немає взагалі
```

Це найдешевша страховка в проєкті: правило перестає залежати від того, чи
згадав про нього автор чергового патча.

---

## 2. Заливка — тільки UPSERT по uid

Ніякого `TRUNCATE`, ніякого масового `DELETE`.

**Як ламається.** Сідер пишуть як «почистити й залити заново» — це швидше й
простіше, і на порожній базі виглядає правильно.

**Перевірка.** Грепом по коду заливки:

```sh
grep -rniE 'truncate|delete from (places|place_uids|place_contacts)' src/
```

Плюс тест: залити той самий набір двічі, звірити, що доданий людиною заклад і
позначки на місці.

---

## 3. Прогін не чіпає рядки origin = 'user'

**Як ламається.** `WHERE origin = 'osm'` забувають в одному з чотирьох запитів
заливки — зазвичай у тому, що оновлює контакти або медіа.

**Перевірка:**

```sql
-- Доданий людиною заклад, який чомусь має відмітку прогону
SELECT uid, name, last_run_id
FROM places
WHERE origin = 'user' AND last_run_id IS NOT NULL;
```

---

## 4. Заклад не видаляється фізично ніколи

**Як ламається.** Обробник модерації робить те, що просить кнопка: «прибрати» →
`DELETE`. Разом із рядком помирають позначки людей і всі роздані посилання.

**Перевірка:**

```sql
-- Позначки, що вказують у порожнечу
SELECT up.uid, COUNT(*) AS marks
FROM user_places up
LEFT JOIN places p ON p.uid = up.uid
LEFT JOIN place_uid_aliases a ON a.old_uid = up.uid
WHERE p.uid IS NULL AND a.old_uid IS NULL
GROUP BY up.uid;
```

Ненульовий результат означає, що рядок закладу зник, а не отримав надгробок.

---

## 5. uid видається раз і не змінюється

Злиття дублів — через `place_uid_aliases`, не через видалення.

**Як ламається** двома способами. Перший: злиття роблять як «перенести позначки
й видалити зайвий рядок» — і старі посилання вмирають. Другий: псевдоніми
шикуються в ланцюжок.

**Перевірка:**

```sql
-- Ланцюжки: old_uid, який сам є ціллю іншого псевдоніма
SELECT a.old_uid, a.uid
FROM place_uid_aliases a
JOIN place_uid_aliases b ON b.old_uid = a.uid;

-- Псевдонім, що веде в неіснуючий заклад
SELECT a.old_uid, a.uid
FROM place_uid_aliases a
LEFT JOIN places p ON p.uid = a.uid
WHERE p.uid IS NULL;
```

Зливаючи `B → C`, коли вже є `A → B`, треба тим же кроком переписати `A → C`.

---

## 6. gid не виходить за межі беку

**Як ламається.** `SELECT *` у репозиторії закладів, і `gid` їде в JSON.
Або потрапляє в бандл, який лежить на публічному URL.

**Перевірка:**

```sh
grep -rn 'SELECT \*' src/ | grep -i place        # явні списки полів, не зірочка
grep -c '"gid"' /var/www/places/places-*.json    # має бути 0, поки не вирішено інакше
```

Умови Google Maps Platform дозволяють **зберігати** `place_id`, але не роздавати
його третім особам. Роздача — це саме публічний файл, а не те, де відбувається
обчислення.

---

## 7. Ручне сильніше за автоматичне

Скасувати ручне рішення може тільки людина.

**Як ламається.** Логіка «Google каже `OPERATIONAL` — знімаємо надгробок»
пишеться без перевірки `source`, і прогін повертає на карту те, що людина
щойно прибрала, подивившись на місці.

**Перевірка** — юніт-тест, не запит: надгробок із `source = 'manual'` плюс
`status = 'OPERATIONAL'` від Google → надгробок лишається на місці.

---

## 8. Записи в place_uids не видаляються ніколи

Це кладовище, з якого відновлюються id.

**Як ламається.** Хтось «прибирає сміття»: рядки, чий `last_seen` старший за
рік і яких немає в `places`. Після цього заклад, що повернувся в OSM, отримає
новий `uid` — і всі позначки на старому осиротіють.

**Перевірка:**

```sql
-- Кількість рядків не має падати між прогонами; звіряти з pipeline_runs
SELECT COUNT(*) FROM place_uids;
```

Найпростіший запобіжник — заборонити `DELETE` на цій таблиці правами (див. 1).

---

## 9. Кожна заливка має run_id і рядок у pipeline_runs

**Як ламається.** Ендпоінт заливки дозволяє писати без відкритого прогону —
зазвичай «щоб швидко полагодити руками».

**Перевірка:**

```sql
-- Заклади з посиланням на прогін, якого немає
SELECT p.uid, p.last_run_id
FROM places p
LEFT JOIN pipeline_runs r ON r.id = p.last_run_id
WHERE p.last_run_id IS NOT NULL AND r.id IS NULL;

-- Прогони, що ніколи не закрились
SELECT id, kind, started_at FROM pipeline_runs
WHERE status = 'running' AND started_at < NOW() - INTERVAL 1 DAY;
```

## 10. Одна картка Google — один наш заклад

**Як ламається.** Збіг рахується для кожної точки окремо, і ніщо не заважає
двом нашим закладам обрати одного кандидата. Так буває, коли Google не знає
одного з них: найкращим для нього стає найближчий сусід, чия назва сяк-так
пройшла поріг. Далі обидва показуються підтвердженими, обидва носять чужий
статус, і коли та картка закриється — з карти зникнуть двоє, хоч живий один.

**Перевірка** — обмеження в схемі, `UNIQUE KEY uq_gid (gid)` у `google_links`.
Запит для наявної бази:

```sql
-- Дві прив'язки на одну картку
SELECT gid, COUNT(*) FROM google_links
WHERE gid IS NOT NULL GROUP BY gid HAVING COUNT(*) > 1;
```

Спір виграє краща схожість назви (`score`), за рівної — менша відстань.
Ручна прив'язка не програє нікому. Переможений лишається без `gid` — це не
втрата, а чесний стан: ми не знаємо, що це в Google.

Окремий випадок, коли не виграє ніхто: жодна зі сторін не набрала порогу.
Тоді прив'язки знімаються обидві — 29.08.2026 таких груп було 12 із 79.

## 11. Прогін зі старою накладкою не запускається

**Як ламається.** `pull:overlay` упав через мережу, людина знизала плечима й
запустила прогін — файли ж на місці, з минулого місяця.

**Перевірка** — на стороні пайплайна: `fetch-places.js` дивиться на
`generatedAt` у завантаженій накладці й **падає**, якщо їй більше доби.
Не попереджає, а падає: попередження в логу на сорок рядків не читає ніхто.

Бек із свого боку пише `pipeline_runs.overlay_at`. Це дає змогу потім
відповісти на питання «чому правка від 3 числа не доїхала» — тому що прогін
почався 2-го.
